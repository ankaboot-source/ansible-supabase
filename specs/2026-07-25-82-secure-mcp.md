# Spec: Secure MCP Remote Access (#82)

- **Issue:** ankaboot-source/ansible-supabase#82 — "Secure MCP"
- **Labels:** `high priority`, `looper:plan`
- **Branch:** `looper/planner/82-secure-mcp` (base: `main`)
- **Date:** 2026-07-25
- **Status:** Proposed

---

## 1. Problem

The Supabase MCP (Model Context Protocol) server is currently **intentionally blocked**. In `roles/supabase/templates/kong-supabase.yml.j2:389-429`, two Kong routes exist:

- `mcp-blocker` (lines 389-402): matches `/api/mcp` → returns HTTP 403 via `request-termination`.
- `mcp` (lines 404-429): matches `/mcp` → upstream `http://studio:3000/api/mcp`, but **hard-locked** with `request-termination` returning 403. A commented-out `cors` + `ip-restriction` block is marked `# danger zone!`.

The MCP upstream is Supabase Studio's own `/api/mcp` endpoint (container `supabase-studio`, image `supabase/studio:2026.06.03-sha-0bca601`, internal port 3000). Studio is published on the host as `127.0.0.1:3001` (loopback only). There is no separate MCP service, no `MCP_SERVER_*` env vars, and **no authentication on the MCP endpoint itself**.

The issue reports that the Supabase MCP server *can* be exposed to the public Internet, and asks for a **secure remote-access solution** so authorized clients can connect **without requiring the service to be publicly accessible**.

Two gaps must be closed:
1. **Exposure gap** — MCP is blocked, not exposed at all. Authorized clients have no path to reach it.
2. **Auth/transport gap** — Studio's `/api/mcp` has no auth of its own. Any path that exposes it must add authentication and encrypted transport; simply unblocking Kong would publish an unauthenticated MCP endpoint to the Internet.

## 2. Goals

- **G1.** Authorized remote clients can connect to the Supabase MCP endpoint over encrypted transport (TLS).
- **G2.** Unauthorized clients (anonymous Internet, unauthenticated users) cannot reach the MCP endpoint.
- **G3.** The MCP endpoint is **not** bound to a public interface; it remains reachable only through an authenticated gateway or a private tunnel.
- **G4.** The solution is **opt-in and data-driven** — configured via `env/supabase.yml`, consistent with the existing `projects:` map pattern in the Caddy role. Default state remains "MCP blocked" (no behavior change for existing deployments that don't enable the feature).
- **G5.** The solution reuses existing infrastructure (Caddy auth gateway, Kong routing) rather than introducing a parallel auth stack.
- **G6.** The feature is documented in `docs/advanced-docs.md` alongside the existing Caddy SSO / UFW / Fail2ban sections.

## 3. Non-Goals

- **N1.** Not replacing or forking Supabase Studio. The MCP upstream stays as Studio's `/api/mcp` endpoint.
- **N2.** Not building a custom MCP auth protocol. Authentication is enforced at the gateway (Caddy) or API gateway (Kong), not inside Studio.
- **N3.** Not exposing MCP over plain HTTP or without authentication in any supported configuration.
- **N4.** Not changing the default deployment posture: MCP stays blocked unless an operator explicitly enables the feature.
- **N5.** Not implementing per-user authorization inside MCP itself (e.g., scoping which tools a given user may call). Out of scope for #82; the unit of access is "authorized client can connect / unauthorized client cannot."
- **N6.** Not introducing a new tunneling role (Cloudflare Tunnel, Tailscale, WireGuard) in this spec. See §6 (Alternatives) for why the gateway approach is preferred; a tunnel role can be a follow-up if the gateway approach is insufficient for specific deployment shapes.

## 4. Design

### 4.1 Approach: Caddy-gated MCP upstream (chosen)

Add MCP as a new entry in the Caddy `projects:` map in `env/supabase.yml`, pointing at `localhost:8000` (Kong) with path `/mcp`, and enable `oidc: true` (or `basicauth` / `allowed_ips`) on that upstream. Caddy authenticates the client, then proxies to Kong, which forwards to Studio's `/api/mcp`.

```
Authorized client ──TLS──▶ Caddy :443 ──auth──▶ Kong :8000 /mcp ──▶ studio:3000 /api/mcp
                            (OIDC/basic/IP)        (unblock route)
```

This reuses the existing Caddy auth gateway (`greenpau/caddy-security` plugin already built into the role) and the existing Kong routing. It requires:

1. **Kong template change** — replace the hardcoded 403 on the `mcp` route with a conditional unblock, gated by a new `mcp_enabled` flag. When `mcp_enabled: false` (default), keep the 403. When `mcp_enabled: true`, remove the `request-termination` plugin so Kong forwards to Studio.
2. **Caddy config change** — add an `mcp` project entry to `env/supabase.yml` `projects:` map, with the operator's chosen auth method (`oidc`, `basicauth`, or `allowed_ips`).
3. **No new role, no new service, no new container.**

### 4.2 Why this approach

- **Reuses existing auth infrastructure.** The Caddy role already supports OIDC (GitHub/GitLab/Discord/generic), basic auth, and IP allow-lists per upstream, all data-driven from `env/supabase.yml`. No new auth code is needed.
- **Keeps MCP off the public interface.** Studio stays bound to `127.0.0.1:3001`; Kong stays on `8000` (loopback-published, default-denied by UFW). The only public-facing surface is Caddy on 443, which authenticates before proxying.
- **Default-deny preserved.** `mcp_enabled` defaults to `false`; the Kong 403 stays unless an operator explicitly opts in. Existing deployments see no behavior change.
- **Single config surface.** Operators enable MCP by editing `env/supabase.yml` only — no template editing, no new role to enable in `playbook-supabase.yml`.
- **Consistent with existing patterns.** The `monitor` project entry (`env/supabase.yml:184-191`) already demonstrates the pattern of a Caddy-protected upstream pointing at a localhost service.

### 4.3 Configuration surface

New keys in `env/supabase.yml` (under a new `# MCP #` section):

```yaml
# ── MCP ──────────────────────────────────────────────────────────────
# Enable the Supabase MCP endpoint (/mcp) through the Caddy auth gateway.
# When false (default), Kong returns 403 for /mcp and MCP is unreachable.
# When true, Kong forwards /mcp to Studio's /api/mcp; Caddy must authenticate
# the client via the mcp project entry below.
mcp_enabled: false

# Caddy project entry for the MCP endpoint. Auth method is chosen per-upstream
# using the existing oidc / basicauth / allowed_ips knobs.
# Uncomment and adapt to enable. Requires mcp_enabled: true.
# projects:
#   mcp:
#     domain: mcp.example.com            #REQUIRED when enabled
#     log_file: /var/log/caddy/mcp.log
#     oidc_enabled: true                 # use SSO_PROVIDER (github/gitlab/discord/generic)
#     upstreams:
#       - targets:
#           - localhost:8000
#         paths:
#           - /mcp
#         oidc: true
#     # allowed_ips: [192.0.2.0/24]     # optional additional IP allow-list
#     # basicauth:                        # optional, alternative to oidc
#     #   - path: /mcp
#     #     username: mcp-user
#     #     password: changeit           #REQUIRED when basicauth used
```

### 4.4 Kong template change

In `roles/supabase/templates/kong-supabase.yml.j2`, the `mcp` route (lines 404-429) currently always applies `request-termination` (403). Wrap that plugin in a Jinja conditional:

```jinja
  - name: mcp
    url: http://studio:3000/api/mcp
    routes:
      - name: mcp
        methods: [GET, POST, OPTIONS]
        paths:
          - /mcp
        strip_path: true
        protocols: [http, https]
{% if not mcp_enabled | default(false) %}
        plugins:
          - name: request-termination
            config:
              status_code: 403
              message: "MCP is disabled. Set mcp_enabled: true in env/supabase.yml and configure the mcp Caddy project."
{% else %}
        # MCP is enabled. Authentication is enforced by the Caddy gateway
        # (oidc / basicauth / allowed_ips on the mcp project entry).
        # Do NOT expose Kong :8000 directly to the Internet without Caddy in front.
{% endif %}
```

The commented-out `cors` + `ip-restriction` block (the "danger zone!" block) is removed — CORS and IP restriction are now handled at Caddy, which is the correct layer for remote-client auth. Kong stays internal.

### 4.5 Validation / safety invariants

- **V1.** With `mcp_enabled: false` (default), `curl http://localhost:8000/mcp` returns 403 (unchanged behavior).
- **V2.** With `mcp_enabled: true` and no Caddy `mcp` project entry, MCP is reachable on `localhost:8000/mcp` but **not** exposed publicly (Caddy has no route for it). This is a transitional/debug state; the docs should warn that `mcp_enabled: true` without a Caddy entry is unsupported.
- **V3.** With `mcp_enabled: true` and a Caddy `mcp` project entry with `oidc: true`, an unauthenticated request to `https://mcp.example.com/mcp` is challenged by Caddy (302 to OAuth provider); an authenticated request proxies through to Studio and returns an MCP response.
- **V4.** With `allowed_ips` set on the `mcp` project, requests from non-listed IPs get 403 from Caddy before reaching Kong.
- **V5.** UFW default rules still deny external access to `8000` (Kong) and `3001` (Studio) — only 80/443 are public. No UFW change required.

## 6. Alternatives considered

### A1. Harden the Kong `mcp` route directly (Kong-layer auth)
Uncomment the `cors` + `ip-restriction` block and add `key-auth` or `oauth2` Kong plugins to the `mcp` route, bypassing Caddy auth.

- **Pros:** No Caddy project entry needed; auth enforced at the same layer as the existing `mcp` route.
- **Cons:** Kong auth plugins are configured in the Kong template (YAML), not in `env/supabase.yml` — breaks the single-config-surface pattern. Kong `key-auth` is API-key auth, not OAuth2/OIDC; weaker than Caddy's `caddy-security` SSO. Kong `oauth2` plugin requires a Kong DB-backed plugin config and a consumer record per client — operationally heavier than reusing Caddy SSO. Kong on :8000 would need to be exposed publicly (or fronted by Caddy anyway), which contradicts the issue's "not publicly accessible" requirement.
- **Rejected:** Worse config ergonomics, weaker auth, conflicts with the "not publicly accessible" requirement.

### A2. New tunneling role (Cloudflare Tunnel / Tailscale / WireGuard)
Introduce a new `roles/cloudflared/` or `roles/tailscale/` role that establishes a private tunnel to the server; authorized clients connect via the tunnel and reach MCP on the private network.

- **Pros:** Strongest match for the literal wording "without requiring the service to be publicly accessible" — the service would have no public surface at all. Works for clients behind NAT.
- **Cons:** No tunneling infrastructure exists in the repo today (verified: zero references to cloudflared, ngrok, tailscale, wireguard, tunnel). Introducing a new role is a much larger change: new role, new systemd unit, new secrets (tunnel tokens / tailscale auth keys), new docs, new UFW rules. Out of proportion for a single-issue spec labeled "plan". Tunnels also don't solve *authorization* — once on the tunnel, any client can reach MCP unless we *also* add auth (which brings us back to the gateway approach).
- **Rejected for #82:** Too large for this spec. Can be a follow-up issue ("Secure MCP via private tunnel") if a deployment needs NAT traversal or a zero-public-surface posture. The gateway approach (chosen) already satisfies "not publicly accessible" in the sense that matters for a typical deployment: MCP is not bound to a public interface, and the only public surface (Caddy :443) authenticates before proxying.

### A3. Do nothing (keep MCP blocked)
- **Rejected:** Does not address the issue's request for authorized remote access.

## 7. Open questions

- **Q1.** Does Supabase Studio's `/api/mcp` endpoint support being reverse-proxied under a path prefix other than `/mcp`? The current Kong route uses `strip_path: true` and forwards to `http://studio:3000/api/mcp`. If an operator wants the MCP endpoint served at `https://mcp.example.com/` (root) rather than `https://mcp.example.com/mcp`, the Caddy upstream path handling needs to match. **Resolution during implementation:** test both `/mcp` and `/` path configurations against Studio and document the supported option(s).
- **Q2.** Does the MCP streamable-transport (SSE / long-poll) work cleanly through Caddy's `caddy-security` auth? MCP over HTTP can use SSE, which requires the proxy to not buffer responses. Caddy's reverse proxy streams by default, but the `authorize` middleware may interfere with long-lived connections. **Resolution during implementation:** test an authenticated SSE MCP session end-to-end and, if needed, add `flush_interval -1` or disable buffering on the MCP upstream in the Caddyfile template.
- **Q3.** Should `mcp_enabled: true` without a Caddy `mcp` project entry be a hard error (fail the playbook) or a soft warning? The spec currently treats it as a soft, unsupported state (V2). **Resolution during implementation:** add an Ansible assertion that fails the play if `mcp_enabled: true` and no `mcp` project exists in `projects:` — fail-fast is safer than a silent half-enabled state. Update V2 accordingly.

## 8. Risks

- **R1.** Unblocking Kong's `/mcp` route (even conditionally) could be misconfigured by an operator who sets `mcp_enabled: true` without adding the Caddy project entry, exposing MCP on `localhost:8000` only — which is still not public (UFW denies 8000), but is a confusing half-state. **Mitigation:** Q3's fail-fast assertion.
- **R2.** Studio's `/api/mcp` may have its own rate limits or auth expectations that conflict with being proxied. **Mitigation:** test end-to-end during implementation; if Studio rejects proxied requests, document the required Studio env vars (if any) in the spec's implementation plan.
- **R3.** The `caddy-security` plugin's `authorize` middleware may not handle MCP's SSE/streaming transport correctly out of the box. **Mitigation:** Q2's end-to-end SSE test; fall back to `basicauth` or `allowed_ips` (which don't go through the `authorize` middleware) if OIDC breaks streaming.
- **R4.** Operators with an existing `projects:` map who add an `mcp` entry must avoid colliding with an existing domain. **Mitigation:** the `mcp` project uses its own subdomain (e.g., `mcp.example.com`); document the subdomain requirement.

## 9. Out of scope / follow-ups

- **F1.** A tunnel-based secure-access role (Cloudflare Tunnel / Tailscale) for deployments that need NAT traversal or a zero-public-surface posture. Separate issue.
- **F2.** Per-user / per-tool authorization inside MCP (scoping which MCP tools a given authenticated user may call). Separate issue; requires Studio-side changes or a policy layer in front of MCP.
- **F3.** MCP client configuration docs (how to point an MCP client at `https://mcp.example.com/mcp` with OAuth2). Belongs in `docs/advanced-docs.md` once the server side is implemented; can be added in Task B or a follow-up.
